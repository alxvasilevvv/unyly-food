# Тесты и что они доказывают

Запуск: `npm test` (нужен PostgreSQL; адрес в `TEST_DATABASE_URL`, по умолчанию `postgres://postgres@localhost:5432/unyly_test`), например `TEST_DATABASE_URL=postgres://postgres:localdev@localhost:5432/unyly_test npx vitest run`. Каждый файл пересоздаёт схему.

Тесты поднимают настоящий HTTP-сервер и ходят в него **официальным MCP SDK Client** через Streamable HTTP. Токен получают через реальный OAuth-поток: DCR → consent с веб-сессией → PKCE → token. Подтверждение выполняется POST-запросом со страницы с CSRF-токеном, как это делает человек.

## Какой провайдер используется

| Уровень | Что | Статус |
|---|---|---|
| Симулятор | `DemoProvider`: синтетический каталог, идемпотентность по ключу, подписанные webhook, прогрессия статусов по часам, инъекция сбоев | **Все автотесты** |
| Sandbox | Grab sandbox (GrabFood POS / GrabExpress) | **Не используется**: нет ключей. API Food/Mart не покрывают потребительские заказы; GrabExpress подходит для `express`, но нужен бизнес-аккаунт |
| Реальный провайдер | Grab Live | **Не используется** |

**Зелёные тесты на симуляторе не означают, что реальные заказы Grab доступны.** Контрактных тестов Live-адаптера нет: документации для потребительских заказов не существует, и писать тесты по выдуманному контракту нельзя.

## Покрытие требований ТЗ (раздел 12)

| Требование | Тест |
|---|---|
| Успешный заказ в Demo | `demo-flow`: «order: cart → quote → checkout → user confirms…» (включая доставку через подписанные webhook) |
| Истечение цены | `safety`: «quote expiry blocks prepare_checkout», «approved confirmation expires before submit» |
| Изменение корзины/адреса/цены после подтверждения | `safety`: «cart change after approval…», «page shows invalidation…», «price change at the provider…», «deleting the cart address…» |
| Невозможность оформить без подтверждения | `safety`: «submit_order without human confirmation…», CSRF, сумма, которую видел человек |
| Повторное и параллельное выполнение | `safety`: «parallel submit_order calls + double web click» (6 вызовов MCP + 2 клика → 1 заказ) |
| Таймаут после принятия провайдером | `resilience`: «timeout after the provider accepted», «…SUBMISSION_UNKNOWN, then resolved by the background job» |
| Восстановление после перезапуска | `resilience`: «crash after provider accepted: a restarted instance reconciles», «crash before the provider received it» |
| Повторные и запоздалые webhook | `resilience`: «deduplicates repeats and ignores late events», подписи, раннее событие |
| Чтение и изменение чужого заказа | `access`: «Bob cannot read or change…», «…open or confirm Alice's pages», инъекция `user_id` |
| Отзыв доступа | `access`: «revoking access in the dashboard…», ротация refresh, повтор кода, удаление аккаунта |
| Отмена с возможным сбором | `orders-edge`: «free before preparation; fee after…», «cannot cancel once picked up» |
| Недоступность провайдера без подмены демоданными | `resilience`: «provider definitely unavailable…», «status read with provider down…» |
| Обход подтверждения текстом из меню | `safety`: «menu text that tries to instruct the assistant…» |
| Прочее | модификаторы, наличие, минимальная сумма, закрытый ресторан, зона доставки, неоднозначный адрес, сборы и скидки, Handoff, недоступность Live, scopes, audience, SSRF в CIMD, деньги |

| Сервисы mart, ride, express | `services`: карта мест на EN/RU/TH, «аэропорт» → `PLACE_AMBIGUOUS` с вариантами, аптека с пометкой о безрецептурных средствах и `QUANTITY_LIMIT` (в том числе по нескольким строкам), обязательная обёртка цветов, `estimate_trip` со сбором за аэропорт и учётом пассажиров, полный путь поездки с аннулированием подтверждения после `set_trip`, одна машина на поездку, вес и лимиты посылок, Handoff поездки со ссылкой Transport, все 8 рынков с пометкой непроверенных ссылок, правка сохранённого адреса в маршруте аннулирует подтверждение |
| Совместимость клиентов | `compat`: метаданные с CIMD и `offline_access`, loopback redirect на любом порту, запрос только `offline_access` ведёт на согласие со всеми scopes, персональный токен работает ровно со своими scopes и показывается один раз, отозванный токен и токен в URL не принимаются, гость не может создать токен |
| Гостевое демо `/try`, тайский язык | `showcase`: парсер запросов на трёх языках, выбор варианта только из серверного расчёта, гость не может выдать OAuth-доступ и добавить passkey, удаление гостей через 24 часа, защита от `?lang=constructor` |

Итог последнего прогона (30.09.2026, после мульти-сервиса): **10 файлов, 103 теста, все прошли**; `npm run typecheck` без ошибок.

### Визуальная проверка редизайна
Playwright (Chromium): главная, `/try` (полный путь запрос → вариант → подтверждение → живой статус), `/for-grab`, `/connect`, `/login` на EN, TH и RU; десктоп 1360 px и телефон 390 px; светлая и тёмная темы. Горизонтальной прокрутки нет, тайский шрифт (Noto Sans Thai) подгружается локально.

### Ревью редизайна
Отдельный агент проверил изменения и нашёл 9 замечаний; все исправлены, основные закрыты тестами в `test/showcase.test.ts`: язык из `?lang=`/cookie принимал имена унаследованных свойств (`constructor`) и ломал страницы; подписи SVG не экранировались; один IP мог исчерпать общий лимит гостей (добавлен лимит на IP и блокировка); парсер пропускал списки аллергенов; `/try/choose` принимал вариант с блокирующими проблемами; гость мог добавить passkey к временному аккаунту; ETA гостевого заказа не учитывал ресторан; бессрочный кэш шрифтов; фраза «nut-free» в макете звучала как гарантия.

## Независимое ревью

Отдельный агент, не участвовавший в написании кода, проверил путь подтверждения, отправки, авторизации и отмены. Он нашёл 6 дефектов, все исправлены и закрыты регрессионными тестами в `test/regressions.test.ts`:
1. Счётчик неверных кодов входа откатывался вместе с транзакцией, поэтому код можно было перебирать. Исправлено: ошибка возвращается после commit.
2. Пока исход первой отправки был неизвестен, по той же корзине можно было создать второе подтверждение и получить **второй реальный заказ**. Исправлено: пока по корзине есть отправка в статусе `in_flight`, `unknown` или `accepted`, новая корзина к отправке не допускается (блокировка корзины, затем checkout).
3. Отмена, прерванная сбоем, зависала в `executing` и блокировала новые отмены. Исправлено: воркер доводит её тем же идемпотентным запросом с лимитом сбора, который одобрил пользователь; при выросшем сборе запрос аннулируется.
4. Параллельные сверки могли откатить итоговый статус. Исправлено: все переходы защищены условием на текущий статус.
5. «Не найден» засчитывался, пока исходный запрос ещё мог выполняться, и реальный заказ мог быть помечен как несуществующий. Исправлено: окно ожидания 3× timeout; закрытые как NOT_RECEIVED попытки перепроверяются 24 часа.
6. Мелочи: сравнение Origin по префиксу (теперь точное), неограниченная очередь «ранних» webhook (теперь с backoff), имя клиента на страницах помечено как «указал сам клиент».
