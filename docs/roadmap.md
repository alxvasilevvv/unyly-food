# Блокеры реального запуска и план следующей версии

## Блокеры

### Для реальных заказов Grab (Live)
| # | Блокер | Кто снимает | Что нужно |
|---|---|---|---|
| B1 | Нет API для заказа Food и Mart от имени покупателя (поиск, меню, цена, создание заказа) | Grab (BD / partnerships) | Партнёрское соглашение и документация consumer-ordering или affiliate API |
| B1a | Нет API бронирования поездок для третьих сторон | Grab (Transport) | Партнёрский ride booking API: бронирование, статус, отмена. Оценки уже реализованы через Partner Farefeed (`GRAB_FAREFEED`, диапазон цены, ETA, surge, deep link в приложение Grab), но нужен scope `ride.estimate`, который Grab выдаёт по соглашению, и правила показа цен (B1c) |
| B1b | Нет ключей GrabExpress Delivery API | Отдел продаж Grab | **Адаптер реализован по публичной документации** (`src/providers/grab/`, флаг `GRAB_EXPRESS`): котировки, создание после подтверждения, webhook, отмена, сверка неизвестного исхода. Проверен только на mock-сервере (`test/support/grab-mock.ts`), в sandbox Grab не запускался. Нужно: sandbox-ключи (OAuth client со scope `grab_express.partner_deliveries`), прогон всех сценариев в консоли Grab, передача webhook URL и секрета, затем production-ключи по городам TH и тарифы |
| B1c | Открытые вопросы к Grab по Live | Grab | Правила показа и кэширования цен Farefeed; политика повторов webhook GrabExpress; разрешено ли агрегатору бронировать от имени многих отправителей; лимиты веса и размера по договору; один OAuth client для sandbox Express и staging Farefeed или два |
| B2 | Нет scope GrabID для заказов и оплаты от имени пользователя | Команда GrabID | Список scopes, регистрация redirect URI, условия |
| B3 | Нет схемы оплаты заказа (GrabPay в контексте Food, Mart и поездок) | Grab | Модель оплаты: оплата в Grab с редиректом или токенизация. Для GrabExpress `cashless` связка сделана: GrabPay One-time Charge до создания доставки, возвраты по правилам из architecture.md. Нужны ключи GrabPay (Integration Manager), согласие Grab на `CASHLESS` с `payer SENDER` для агрегатора и прогон в окружении Grab |
| B4 | Нет документированной подписи webhook и статусов потребительского заказа | Grab | Спецификация событий и схема подписи |
| B5 | Нет гарантий идемпотентности создания заказа | Grab | Поле idempotency key или поиск заказа по нашему ключу. Для GrabExpress обойдено без повторной отправки: `merchantOrderID` = id попытки, ожидание webhook, затем отмена по `merchantOrderID` (см. architecture.md). Ключ идемпотентности у Grab всё равно нужен |
| B6 | Юридическое: PDPA Таиланда, оферта, ответственность за заказ, возвраты | Юрист | Политика данных, оферта, DPA с Grab |

Черновик обращения к Grab - `grab-partner-request.md` (**не отправлен**).

## План следующей версии (по приоритету)

1. **Ручная проверка** ассистентов из `/connect` и Claude Code; обновить `clients.md` статусами «проверено».
2. **Обращение в Grab** (B1–B5, включая ride booking API и ключи GrabExpress) и параллельно встреча с командой Partner Apps: мини-приложение внутри Grab может дать вход и оплату без консьюмерского API.
3. ~~**Повторное подтверждение для крупных сумм** (passkey / WebAuthn) на страницах подтверждения - до включения Live.~~ **Сделано.** Порог по валюте (`STEP_UP_THRESHOLD_<CUR>`, по умолчанию около 2 000 THB / 55 USD, `STEP_UP=off` выключает); для пользователей с passkey кнопка «Подтвердить» запрашивает подпись, привязанную к этому подтверждению (2 минуты, одноразово). Без passkey поток прежний, с рекомендацией добавить ключ. См. threat-model.md, T22.
4. **Live-адаптер** за feature-флагами по каждой возможности. Контрактные тесты по документации Grab, прогон в их sandbox (staging-окружение есть у GrabFood POS API и GrabExpress).
5. **MCP URL-mode elicitation** (спецификация 2025-11-25 / 2026-07-28): клиенты с поддержкой смогут открывать страницу подтверждения сами. Страница Unyly остаётся единственным источником согласия.
6. **Переход на ревизию MCP 2026-07-28**, когда официальный SDK её поддержит (сервер уже stateless, состояние в серверных handle).
7. **Дымовой тест подписки** (см. product.md) и дашборд метрик.
8. **GrabExpress как первый Live-сервис**: адаптер за флагом `GRAB_EXPRESS` написан и покрыт контрактными тестами на mock-сервере. Режим `cashless` связан с оплатой GrabPay (оплата до создания доставки, возвраты при отказе и отмене до забора, `awaiting_payment` в MCP), тоже только на mock-серверах. Осталось: ключи GrabExpress (B1b) и GrabPay, прогон в sandbox Grab по чек-листу из operations.md (cash, затем cashless), процесс поддержки для случаев `support`, затем production в одном городе.
9. Масштабирование: общий rate-limit (Redis или Cloudflare), managed Postgres, реплики приложения (сервер stateless).
