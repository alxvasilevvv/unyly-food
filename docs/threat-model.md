# Модель угроз

Активы: деньги пользователя (в Live), его согласие на заказ, адреса и email, токены ИИ-клиентов, целостность заказов.
Действующие лица: пользователь; ИИ-модель (может ошибаться или поддаться инъекции); ИИ-клиент (приложение); злоумышленник в сети или с чужим аккаунтом; скомпрометированный провайдер, ресторан или магазин (недоверенный контент).

## Остаточные риски

- **Скомпрометирована почта пользователя** - злоумышленник войдёт и подтвердит заказ ниже порога step-up. Крупные заказы требуют passkey (T22), но только если он добавлен: у аккаунта без passkey защиты сверх сессии нет, поэтому страница подтверждения советует его добавить. Вход по коду из почты также позволяет добавить свой passkey; это закрывается только отказом от входа по почте для аккаунтов с passkey (не сделано).
- **Персональный токен живёт дольше OAuth-токена** (до 365 дней, без ротации). Утечка даёт доступ к подготовке и, при scope `orders:submit`, к отправке уже подтверждённых человеком заказов, но не к подтверждению. Одобрение крупных заказов дополнительно требует passkey (T22).
- **Спецификация MCP считает аннотации недоверенными.** Если клиент их не учитывает, модель может вызвать `submit_order` без вопроса. Это безопасно: без одобрения на сайте вызов вернёт `CONFIRMATION_REQUIRED`.
- **DNS rebinding для CIMD** закрыт закреплением IP. Изменение цели после резолва (TOCTOU) не играет роли, потому что соединение идёт на проверенный IP.
- **Секреты** лежат в `.env` на хосте. Для production нужен менеджер секретов (Doppler, 1Password Connect, AWS/GCP Secret Manager); см. operations.md.
- **Вход через Grab доверяет Grab.** Кто владеет аккаунтом Grab, входит в связанный аккаунт Unyly; утечка аккаунта Grab равна утечке почты (step-up T22 защищает крупные заказы при наличии passkey). Подтверждённость email определяется полем `email_verified` от Grab; если Grab его не передаёт, новые аккаунты через Grab не создаются.
- **GrabPay.** Unyly не видит и не хранит данные карт (оплата на стороне Grab). Access token Grab для возвратов хранится зашифрованным; утечка БД вместе с `GRABPAY_TOKEN_KEY` и `GRABPAY_CLIENT_SECRET` позволила бы делать возвраты на кошельки самих плательщиков, но не списания. Деньги merchant-кошелька выводятся ежедневно, поэтому возврат может временно не пройти.
- **Cashless GrabExpress: Unyly платит Grab.** Доставку Grab выставляет Unyly, а деньги пользователя приходят через GrabPay. Если доставка сорвалась после забора, Grab может взять плату (возврат посылки), а пользователь ждёт возврата: такие случаи не возвращаются автоматически и уходят в поддержку (`live_payment_settlements.outcome = 'support'`). Доставка, найденная после возврата «не получено», тоже уходит в поддержку. Поток проверен только на mock-серверах Grab, не в sandbox Grab.
- **Юридическое** (PDPA Таиланда, оферта, возвраты) до запуска Live требует проверки юристом.
